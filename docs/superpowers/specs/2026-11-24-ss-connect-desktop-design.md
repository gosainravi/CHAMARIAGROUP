# SS-Connect Desktop — Design Spec

Date: 2026-11-24 · Status: draft for review

## 1. Goal

A Windows desktop app, in the style of UltraViewer/AnyDesk, that lets one PC (A, the controller) see another PC's screen (B, the shared PC) and, only with B's permission, control its mouse and keyboard. It is separate from the browser tool at `remote/index.html`; the download is linked from that portal page.

Success means: two Windows PCs on any networks (same office LAN, home broadband, Jio/Airtel mobile hotspot) can connect by ID + password within ~10 seconds, A sees B's screen smoothly enough for IT support, and control only ever happens after B clicks Allow.

## 2. Users and scope

- First users: Chamaria Group staff and IT (internal). Public use later.
- Platform: Windows 10/11 only. Mac later.

In version 1:
- Show own ID + password; connect to a partner by ID + password.
- Live screen view (view-only by default).
- "Ask control" → Allow/Deny popup on B → mouse + keyboard control.
- B can stop control or end the session at any time; a red bar on B shows while controlled.
- 40-minute session limit, enforced by the server, with a warning at 35 minutes.
- Direct connection first, automatic fallback to relay.

Not in version 1: file transfer, chat, clipboard sync, unattended access, multi-monitor switching (primary monitor only), control of UAC/admin prompts, running as a Windows service, accounts/subscriptions, Mac.

## 3. Architecture

Three parts:

1. **SS-Connect app** (same app on A and B) — C#, .NET Framework 4.8, WinForms. .NET Framework 4.8 ships with Windows 10 (1903+) and 11, so users install nothing extra.
2. **Signaling server** — Node.js WebSocket service. Registers each running app's ID, checks passwords, pairs A with B, relays connection setup messages, and owns the session timer.
3. **TURN relay** — coturn. Carries the session only when a direct connection is impossible.

Parts 2 and 3 run on one small cloud VM (Azure B1s or AWS t3.micro, free tier for testing). The server address is a setting in the app, not hard-coded.

### Connection: direct first, relay fallback

The app uses WebRTC via the SIPSorcery library (pure C#, works on .NET Framework 4.8). WebRTC's ICE process tries, in order: same-LAN direct → direct through routers (STUN) → relay through coturn (TURN). All traffic is encrypted (DTLS). This is the AnyDesk/TeamViewer pattern.

Two WebRTC data channels per session:
- `screen` — unordered, unreliable-friendly: compressed screen tiles B → A.
- `control` — ordered, reliable: input events A → B, plus control messages (ask/allow/deny/stop/end).

### Screen pipeline (B → A)

- Capture the primary monitor ~12 fps (GDI BitBlt; DXGI Desktop Duplication can replace it later).
- Split into 64×64 tiles; send only tiles that changed since the last frame.
- Encode changed tiles as JPEG (quality ~70, adjustable); send a full keyframe every 5 s and on request so A recovers from lost tiles.
- A draws tiles into a bitmap and scales it to its window.

Rationale: tile diffs + JPEG need no native video codec, keep the app small, and are light on bandwidth for office screens that mostly sit still.

### Control pipeline (A → B)

- A sends input only after B allowed control. Coordinates are normalized (0–1) to B's screen.
- Events: mouse move, button down/up (left/right/middle), wheel, key down/up (virtual-key codes, so Ctrl/Alt/Shift/Win combos work).
- B injects them with Win32 `SendInput`. B ignores every input event unless control is currently granted — the check lives on B, not A.

## 4. Session flow

1. B opens the app → it registers with the server → shows a 9-digit ID and a random 6-character password (new password each app start; user can refresh it).
2. A enters B's ID + password → server checks → if correct, pairs them and starts the session timer; wrong password 5 times → that ID is locked for 5 minutes.
3. WebRTC connects (direct or relay); A sees B's screen, view-only.
4. A clicks **Ask control** → B sees a topmost popup: "‹A's ID› wants to control your PC — Allow / Deny" (auto-deny after 30 s).
5. Allow → A gets control; B sees a red bar: "Your PC is being controlled — Stop control | End session". Deny → A stays view-only and may ask again.
6. Session ends when A or B clicks End, either app closes, the connection is lost for > 30 s, or the server's 40-minute timer expires (warning to both at 35 min).

## 5. Signaling server

Node.js + `ws`, one process. Messages are JSON over a WebSocket (wss with a TLS certificate from Let's Encrypt on the VM).

- `register {id}` → server stores the socket under that ID (IDs are generated by the server to avoid collisions).
- `connect {targetId, password}` → server forwards a password check to B; B answers yes/no. Passwords are never stored on the server.
- `signal {sdp|candidate}` → forwarded between the paired apps.
- `session-warning` at 35 min and `session-end` at 40 min, sent to both.
- `GET /turn-credentials` → short-lived coturn credentials (shared secret, `use-auth-secret`), so no long-term TURN password is in the app.

Subscription hook: the 40-minute limit is one server-side check; later it looks up the account's plan instead.

## 6. App UI (one main window)

- Left panel "Allow remote control": Your ID, Password (with refresh), status.
- Right panel "Control a remote computer": Partner ID, password, Connect.
- Session window (A): the remote screen, toolbar with Ask control / Release control, quality (Low/Medium/High), timer, End.
- B during a session: small always-on-top bar with timer and End; red bar while controlled.

## 7. Errors

- Server unreachable → "Cannot reach SS-Connect server — retrying" with automatic retry; ID shows once connected.
- Partner offline / wrong ID → clear message within 5 s.
- Wrong password → message; lockout message after 5 tries.
- Connection drop → "Reconnecting…" for up to 30 s, then session ends.

## 8. Security

- Encrypted end to end by WebRTC (DTLS/SRTP-equivalent for data channels); signaling over wss.
- Control only after explicit Allow on B; B enforces it.
- Password: random per app start, checked on B, lockout after 5 wrong tries.
- No secrets in the public GitHub repo: TURN secret and server TLS keys live only on the VM.

## 9. Build and delivery

- Repo folder `desktop/` (app) and `server/` (signaling + coturn setup script).
- GitHub Actions (windows-latest) builds `SS-Connect.exe` on each push to `desktop/`, publishes it to a GitHub Release, and the portal's download button points at that release.
- Unsigned in v1 → Windows SmartScreen shows "Unknown publisher"; users click More info → Run anyway. Code signing later.
- Local development needs the .NET 8 SDK installed on this PC (it can build .NET Framework 4.8 apps).

## 10. Testing

- Server: automated tests for register/connect/password/lockout/timer messages.
- App: unit tests for tile diffing, coordinate mapping, and the "ignore input unless granted" rule.
- End to end on this PC: local server + two app instances; check connect, view, Ask control, Allow, Deny, Stop, typing (no doubled keys), clicking, 40-minute timer (shortened to 1 minute via a test setting).
- Then: real test between two PCs on different networks once the VM is up; confirm one session goes direct and one forced through the relay.

## 11. Open items for the user

- Create the Azure (or AWS) account and VM; Claude provides the setup script.
- Point a domain/subdomain at the VM for the wss certificate (or use the VM's DNS name).
